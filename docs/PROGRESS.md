통합: **`writeStudentRow`** — `saveProgress`·`submitResponse`·`enterLesson`이 락 조건·재조회·

### 세션 24 — 렉 줄이기 A~F + 데이터 유실 버그 (08-20, 버전 27)

| | 무엇 | 실측 |
|---|---|---|
| A~C | 인덱스 행 캐시(300초, 고치는 **8곳**에서 무효화) · 루트 폴더 ID를 스크립트 속성에 · 핸들 재사용 | 인덱스+시트열기+행탐색 **2.09s → 0.60s** |
| D | `enterLesson` — 진입을 **한 번의 왕복**으로 | 12명 동시 입장 실패 0 |
| E | `gradeAnswers` — 여러 문항 **한 번에** 채점 | 9문항 **10.7s → 2.40s** |
| F | 락 안 재조회를 **스냅샷 이후 행만** | 임계구역 단축 |

**H(Sheets API v4)는 사용자 지시로 제외** — 이득은 가장 크지만 백엔드 전면 재작성이라 위험하다.
⚠️ **`gradeAnswer` 1.2초는 Apps Script의 바닥값**(HTTP 왕복 + 스크립트 기동)이라 캐시로 못 내린다 —
줄일 수 있는 건 **횟수**뿐이라 D·E를 넣었다.

**★ 답이 사라지는 기존 버그를 찾았다** — `ensureQuestionColumns`는 컬럼만 만들고 값은
`upsertResponseRow`가 맨 마지막에 한 번의 `setValues`로 쓴다. 그래서 **한 저장에서 새 문항이 둘
이상 생기면** 먼저 만든 컬럼이 아직 비어 있어 다음 문항이 그 자리를 빼앗는다.
고침: 이번 실행에서 만든 컬럼을 기억해 재활용 대상에서 뺀다(`getLastColumn()`이 버퍼 때문에 낡을
수 있어 더 큰 쪽을 쓴다). **지금까지 안 터진 이유**: 슬라이드마다 문항이 1~2개라 컬럼이 한두 개씩
나뉘어 만들어졌다. 기존 데이터 점검 결과 **F6YZ6C 138명 중 137명 정상**.

**★ 숫자 제한만으로는 부족하다** — `digitsOnly`는 숫자 아닌 글자를 지울 뿐 **남은 숫자가 이어
붙는 것은 막지 않는다**(`2학년 3반` → `23`). 학생 화면에 그럴듯한 숫자가 떠서 아무도 눈치채지
못한다. → 값을 대신 고치지 않고(무엇을 뜻했는지는 학생만 안다) **버린 글자를 알려 주는 경고**를
붙였다(`droppedNonDigits`, 사용자가 선택). 색만이 아니라 글자로도 알린다.

### 세션 23 — 채점이 렉을 만드는가 (08-20, 버전 24)

**정오답 공개 시점의 차이**: `immediate`는 학생을 안 막지만 문항 수만큼 왕복하고,
`onSlideLeave`는 **「다음」이 막힌다**. `onFinish`/`never`는 왕복 0회.
12명 학급 기준 서버 누적 실행시간 **293초(즉시) vs 197초(제출 후)**.

**진짜 병목은 채점이 아니라 「입장 때 행 생성」이었다** — 입장 20.9s(락) / 자동저장 6.1s /
제출 5.1s. 제출 때는 행이 이미 있어 락을 안 탄다.

고친 것: `readLesson`에 **캐시가 아예 없었다**(요청마다 Drive 왕복 3.3초 → 120초 캐시) ·
`findRowIndexForRecord`가 시트 전체를 읽던 것을 **1~5열만** · 학생 행 생성 락 대기를 **120초**로
(기다리는 건 느릴 뿐이지만 실패는 수업에 못 들어간다).

실측: `getLesson` 3.29→**1.98s** · `gradeAnswer` 2.66→**1.19s** · `saveProgress` 7.40→**3.49s** ·
12명 동시 제출 **2건 실패 → 0건** · 30명 동시 입장 **0건 실패·중복 0**(최대 44.6s).

## 미해결 이슈

**아직 남은 성능 한계**

- 30명이 **같은 순간에** 입장하면 마지막 학생은 수십 초를 기다린다(실패는 안 한다).
  임계구역의 `SpreadsheetApp.flush()` 두 번이 대부분인데 **중복 방지에 필수라 뺄 수 없다.**
- 부하 시험 중 요청 하나가 250초까지 안 돌아온 적이 있다(나머지는 3초대). 이후 단일 요청은
  정상이라 **일시적 현상으로 보이나 원인은 특정하지 못했다.** 다시 보이면 기록할 것.

**이 환경(claude-in-chrome)에서 되풀이되는 것 — 재시도하지 말고 바로 우회할 것 ★**

- **`computer` 툴이 불안정하다.** `Page.captureScreenshot`이 자주 타임아웃되고, 프로그래매틱
  `.focus()`/`.click()` 후에도 `document.hasFocus()`가 계속 `false`다(이 탭이 OS 차원에서
  포그라운드로 취급되지 않는다). **우회**: `javascript_tool`로 DOM에 이벤트를 직접 디스패치하고
  `document.body.innerText`·`localStorage`로 결과를 확인한다.
- **탭이 `document.hidden:true`로 유지된다** → `IntersectionObserver`·`requestIdleCallback`·
  Page Visibility에 의존하는 기능은 자동화로 발동하지 않는다. 백엔드 API를 직접 부르거나
  React 파이버 훅 `dispatch`로 상태만 강제해 나머지 로직을 확인한다.
- **`javascript_tool`이 45초 타임아웃을 던져도 페이지 안 스크립트는 계속 돌 수 있다.**
  타임아웃을 실패로 오판해 같은 삽입을 반복했다가 문항이 중복 생성된 적이 있다.
  **타임아웃을 받으면 먼저 `localStorage`·화면 상태를 읽어 실제로 실패했는지부터 확인할 것.**
- **네이티브 `confirm()`/`alert()`를 띄우는 버튼을 클릭하면 CDP 연결 전체가 멈춘다.**
  이미 멈춘 탭은 되살릴 수 없다 — 새 탭을 열어 다른 작업을 잇고 사용자에게 직접 눌러 달라고 한다.
- **SPA에서 같은 라우트로의 네비게이션은 컴포넌트를 리마운트하지 않는다.** `?key=` 같은
  **같은 경로·다른 쿼리**를 열어도 `useState` 초기값이 다시 안 읽힌다 —
  새 마운트를 확인해야 하는 검증은 반드시 `location.reload()`로.
- **서브에이전트로 브라우저를 병렬 조작할 때** 같은 Chrome 세션을 다른 세션(사용자의 수동 조작
  포함)과 공유하면 탭이 예기치 않게 다른 URL로 튕기거나 닫힐 수 있다.
- **`resize_window`가 실제로 뷰포트를 못 바꾸는 경우가 있다.** 반영 여부를 `window.innerWidth`로
  먼저 확인하고, 안 먹히면 실제 기기를 쓴다.
- **winget이 이 셸에서 동작하지 않는다.** 도구 설치가 필요하면 portable 배포판을 찾거나
  사용자에게 직접 설치를 요청할 것.
