### 세션 24 — 렉 줄이기 A~F, 그리고 그 과정에서 찾은 데이터 유실 버그 (2026-08-20)

**`Code.gs` 버전 27 배포 완료.** 세션 23에서 목록으로만 냈던 방안을 A→B→C 먼저, 검증 후 D·E·F 순으로 적용했다.

| | 무엇 | 실측 |
|---|---|---|
| **A** | 인덱스 행 캐시 (300초). 인덱스를 고치는 **8곳**에서 무효화 | 인덱스+시트열기+행탐색 **2.09s → 0.60s** |
| **B** | 루트 폴더 ID 를 스크립트 속성에 — Drive 검색 대신 `getFolderById` | (A 에 포함) |
| **C** | 실행당 폴더·스프레드시트 핸들 재사용 | (A 에 포함) |
| **D** | `enterLesson` — 진입을 **한 번의 왕복**으로 (getProgress + saveProgress) | 12명 동시 입장 실패 0 |
| **E** | `gradeAnswers` — 여러 문항 **한 번에** 채점 | 9문항 **10.7s → 2.40s** |
| **F** | 락 안 재조회를 **스냅샷 이후 행만** | 임계구역 단축 |

**H(Sheets API v4)는 사용자 지시로 제외.** 이득은 가장 크지만 백엔드 전면 재작성이라 위험이 크다.

⚠️ **`gradeAnswer` 1.2초는 Apps Script 의 바닥값**이다(HTTP 왕복 + 스크립트 기동). 캐시로 못 내린다 — 줄일 수 있는 건 **횟수**뿐이라 E·D 를 넣었다.

**★ 그 과정에서 답이 사라지는 버그를 찾았다 (기존 버그, 내가 만든 것 아님)**

`ensureQuestionColumns` 는 컬럼을 만들고, 값은 `upsertResponseRow` 가 **맨 마지막에 한 번의
`setValues`** 로 쓴다. 그래서 **한 저장에서 새 문항이 둘 이상 생기면**, 먼저 만든 컬럼이 아직
값이 비어 있어 다음 문항이 「빈 컬럼이네」 하고 **그 자리를 빼앗는다.** 앞 문항의 답이 통째로
사라진다 — D·E 검증에서 실제로 q1 이 없어졌다.

- 고침: 이번 실행에서 만든 컬럼을 기억해 재활용 대상에서 뺀다. `getLastColumn()` 이 버퍼 때문에
  낡을 수 있으므로 그 값과도 비교해 더 큰 쪽을 쓴다.
- **지금까지 안 터진 이유**: 슬라이드마다 문항이 1~2개라 컬럼이 한두 개씩 나뉘어 만들어졌고,
  앞 컬럼에 이미 값이 있어 재활용 대상에서 걸러졌다.
- **기존 데이터 점검 결과 F6YZ6C 138명 중 137명 정상.** 부분 저장 26명은 전부 「앞에서부터
  연속」 = 끝까지 못 푼 학생(강제 제출)이고 충돌 흔적이 아니다.

**★ 숫자 칸에 `23` 이 들어온 이유 — 숫자 제한만으로는 부족하다**

`digitsOnly` 는 숫자 아닌 글자를 지울 뿐 **남은 숫자가 이어 붙는 것은 막지 않는다.**
한 글자씩 정규화해도 `2학년 3반` → `23`, `2-3` → `23`, `2학년 3반 10번` → `2310` 이 된다.
학생 화면에 그럴듯한 숫자가 떠서 아무도 눈치채지 못한다.
→ 값을 대신 고치지 않고(무엇을 뜻했는지는 학생만 안다) **버린 글자를 알려 주는 경고**를 붙였다
(`droppedNonDigits`, 사용자가 3번 방식 선택). 색만이 아니라 글자로도 알린다.

⚠️ **F6YZ6C 의 「23반 10번 오현탁」은 2학년 3반 10번**이다(3반은 10번만 비어 있다). 시트에서 손으로 고칠 것.

**남은 것**
- 30명이 **같은 순간에** 입장하면 여전히 수십 초 걸린다(실패는 안 한다). 임계구역의
  `SpreadsheetApp.flush()` 두 번이 대부분인데 중복 방지에 필수라 뺄 수 없다.
- 부하 시험 중 요청 하나가 250초까지 안 돌아온 적이 있다(나머지는 3초대). 이후 단일 요청은
  정상(1.35초)이라 **일시적 현상으로 보이나 원인은 특정하지 못했다.** 다시 보이면 기록할 것.

### 세션 22 — 응답 행 중복 생성 (2026-08-19)

**`Code.gs` 버전 22 배포 완료 · 프런트 `index-9rQw5D1z.js` 배포 완료.**

마찰전기 수업(F6YZ6C)에서 1반 3번 학생이 **이중으로** 들어와 있었고 수업 중엔 3중으로도 보였다.
데이터를 열어 보니 두 행의 **studentKey가 같았다** — 식별값이 갈린 게 아니라 **행이 두 번 만들어진** 것이다.
(97명 중 식별값 변형으로 갈린 학생은 0명이었다.)

**원인**: `withLock` 이 `SpreadsheetApp.flush()` 없이 락을 놓았다. 시트 쓰기는 **실행이 끝날 때**
커밋되는데 `releaseLock()` 은 그 전이라, 락을 넘겨받은 다음 실행이 읽어도 앞 실행이 만든 행이 안 보인다.
락 안에서 행을 다시 찾는 코드는 이미 있었지만 **flush 가 없어 재조회가 무의미**했다.
학생이 진입 화면을 두 번 통과하면(기기·브라우저 교체, 로컬 저장 전 새로고침) 두 요청이 겹쳐 실제로 났다.

**고친 것**

| 지점 | 내용 |
|---|---|
| `withLock` | 임계구역 **앞뒤로 `flush()`** — 앞 실행의 커밋을 보고, 내 쓰기를 커밋한 뒤 넘긴다 |
| `findRowIndexForRecord` | 열쇠 → 없으면 **다듬은 식별정보**로 대조. 기기가 바뀌어도 이어서 푼다 |
| `getProgress` | `identity` 를 함께 받는다 (types·liveClient·mock·adapters 전부) |
| `lib/identity.ts` | 다듬기 규칙을 여기 하나로. **앞자리 0 제거(03=3)·NFC 정규화** 추가 |
| `lib/studentKey.ts` | 열쇠도 그 규칙을 거친다 (예전엔 `trim().toLowerCase()` 뿐이었다) |
| `upsertResponseRow` | 기존 행의 **열쇠를 보존**한다 — 덮어쓰면 다른 기기와 또 어긋난다 |
| `Player.tsx` | 진입 **즉시** 기기에 저장 (800ms 디바운스 전 새로고침이 재진입을 불렀다) |
| `EntryScreen.tsx` | 「시작하기」 중복 클릭 차단 |
| `mergeDuplicateResponses` | 이미 생긴 중복을 합치는 정비용 액션 (`dryRun: true` 로 먼저 확인) |

**실서버 검증** (테스트 수업을 만들어 실제로 돌리고 삭제)

| 시나리오 | 결과 |

| 같은 학생이 동시에 두 번 진입 | 행 1개 ✔ |
| 다른 기기·다른 표기(`01`/`03`/`고 승현`)로 이어받기 | 답 그대로 이어받음 ✔ |
| 그 상태로 저장 | 행 1개 유지, 원래 열쇠 보존 ✔ |
| 다른 학생(1반 4번) 추가 | 행 2개 ✔ |

| 학생 12명 동시 제출 | **6/12 실패** (락 시간초과) | **12/12 성공**, 전체 6.9초 |

**① 시트 읽기 줄이기**
- `readMetaMap`을 **실행당 한 번**만 (`_metaCache`). 예전엔 `rowToRecord`가 **행마다** 불러 55명이면 55번, `ensureQuestionColumns`는 **문항마다** 불러 저장 한 번에 9번을 더 읽었다. **시트를 고치는 쪽은 반드시 `invalidateMetaCache`를 부를 것.**
- `upsertResponseRow`가 **행 전체를 `setValues` 한 번**으로 쓴다. 예전엔 고정칸 1회 + 문항마다 최대 3회 = **최대 28번의 개별 쓰기**였다. 손대지 않는 칸을 지우지 않으려면 `existingRow`를 넘겨야 한다.
- `getLive`가 수업을 두 번 읽던 것을 한 번으로. 결과 캐시 6초 → 60초(쓰기가 즉시 무효화하므로 안전).

**② 전역 락을 통째로 잡지 않는다 ★**

`LockService.getScriptLock()`은 **모든 수업·모든 학생이 공유하는 하나뿐인 락**이다. `saveProgress`·`submitResponse` 전체가 그 안에 있어서, 한 명이 5초를 잡으면 나머지가 줄을 섰고 20초 한도를 넘긴 학생부터 실패했다.

락이 정말 필요한 건 **구조를 바꾸는 두 경우**뿐이다 — **새 학생의 행을 만들 때**(두 명이 같은 `getLastRow()+1`을 집으면 서로 덮어쓴다)와 **새 문항 컬럼을 만들 때**. 학생마다 자기 행 하나만 쓰므로 **이미 있는 행 갱신은 락이 필요 없다.** `needsNewQuestionColumns()`로 판정하고, 락을 잡은 경우에는 **안에서 행 번호를 다시 찾는다**(기다리는 동안 다른 요청이 만들었을 수 있다).

**③ 저장 시점 조정 (프런트엔드)**

답이 바뀔 때마다 서버로 보내던 것을 **슬라이드 이동 시 + 60초 주기 + 화면 이탈 시**로 바꿨다. 문항 9개 수업이면 학생당 14회 → 6회 안팎. **localStorage 저장은 예전처럼 답이 바뀔 때마다** 하므로 같은 기기 새로고침 복구는 그대로다.

**④ 「멈춤」 판정 폐지 (사용자 지시)**

③으로 저장 주기가 늦어지면 **한 슬라이드에서 오래 고민하는 학생이 「멈춤」으로 뜬다.** 없는 문제를 있다고 알리느니 판정을 걷어냈다. 「마지막 활동 N분 전」 표시는 남겼다(사실만 보여주고 판단하지 않는다). 정렬 기본값은 「도움 필요 순」 → **「진행 느린 순」**.

### 세션 19 — 재발행 때 정답이 바뀌었으면 재채점을 묻는다 (2026-08-18)

**배포 완료 — `Code.gs` 버전 18** (배포 ID·웹앱 URL 그대로). `forceSubmit`·`regradeResponses` 둘 다 실서버에서 확인했다:

- `regradeResponses` + 현황 암호 → `편집 권한이 없습니다` (편집 키 전용이 지켜진다)

**배포가 막혔던 이유와 푼 방법**: Chrome 확장이 "연결되지 않음"이었는데, 원인은 단순히 **Chrome이 실행 중이 아니었던 것**이다(사용자 지적). `Start-Process chrome`으로 띄우니 바로 붙었다. 다음에 확장이 안 붙으면 **Chrome이 떠 있는지부터 확인할 것.** 저장은 이번에도 **첫 시도가 실패**하고 재시도에서 성공했다(문서에 적힌 그대로).

**배경**: 교사가 정답을 잘못 넣었다가 고쳐 재발행해도, **이미 제출된 응답의 점수는 옛 정답으로 매겨진 채** 남는다. 결과 화면에 틀린 점수가 그대로 보인다.

**감지를 어디서 하나** — 에디터가 **자동저장**을 하므로 발행 시점엔 서버에 이미 새 정답이 있다. 서버끼리 비교할 수가 없다. 그래서 **에디터가 수업을 불러온 순간의 정답을 `useRef`에 잡아 두고**, 발행할 때 현재 것과 비교한다.

**무엇을 "정답 변경"으로 보나** — 지문·해설만 고쳤을 때 물어보면 교사가 확인창을 습관적으로 넘기게 되고 정작 진짜 변경을 놓친다. 그래서 **각 채점기가 실제로 읽는 필드만** 비교한다(`lib/answerKey.ts`). 배점 변경도 점수를 바꾸므로 포함하고, 문항 추가·삭제도 잡는다. 채점기가 없는 유형(사진·그림·데이터표)은 아예 제외한다.

⚠️ **`GRADING_FIELDS`는 각 문항의 `grade:` 구현과 짝이 맞아야 한다.** 어긋나면 정답을 바꿔도 안 물어본다(조용한 실패). `answerKey.test.ts`가 **채점기가 있는데 목록에 없는 유형**을 찾아 실패시킨다 — 다만 **기존 유형에 필드가 늘어난 것**까지는 못 잡으니 채점기를 고칠 때 같이 볼 것.

**서버** — 새 액션 `regradeResponses(code, editToken)`. 제출된 행만 현재 정답으로 다시 채점해 점수를 덮어쓴다. **학생이 쓴 답은 건드리지 않는다.** 아직 제출 안 한 학생은 그대로 둔다(제출할 때 어차피 새 정답으로 채점된다). **편집 키 전용** — 점수를 바꾸는 일이라 현황 암호로는 못 하게 했다.

**규칙 13 적용 사례**: `handlePublish`에서 비교가 도는 시점은 **발행이 이미 성공한 뒤**다. 비교가 예외를 던지면 발행이 실패한 것처럼 보인다. 그래서 감쌌는데, **조용히 넘기지 않고** 판정 실패 시 오히려 재채점을 물어보게 했다(재채점은 점수만 다시 계산하는 안전한 작업이라, 헛물어보는 편이 놓치는 것보다 낫다).

**검증**: typecheck / 테스트 **356개**(347→356) 통과. 새 테스트 9개 — 정답 변경 감지 6개(지문만 고친 것은 안 잡는 것, 배점·문항 추가삭제는 잡는 것, 드리프트 방지 포함), 재채점 3개(점수만 바뀌고 답은 그대로, 제출 전 학생 제외, 편집 키 전용).

### 세션 16 — 현황판이 흰 화면이 되던 원인 (2026-08-18)

**증상**: 수업 중 교사가 현황판에 못 들어갔다. `불러오는 중…` 뒤 화면이 통째로 하얘진다. 학생 참여는 정상이었다.

**원인 — 학생 한 명의 답 하나가 학급 전체 화면을 무너뜨렸다.**

`Cloze.tsx`의 `isAnswered`가 `values.every((v) => v.trim()...)`였는데, 저장된 값에 `null`이 있었다:

```
9반 11번 이유림  q3-1  ["전자", null, "(+)전기"]
9반 13번 정예승  q3-1  ["전자", null, "(−)전기"]
```

`null.trim()` → TypeError → React가 트리를 통째로 내려 흰 화면. 현황판은 전원의 답을 훑으므로 **한 명만 이래도 전부 안 보인다.**

`null`이 생긴 뿌리는 같은 파일 Viewer의 `setValue`였다. `[...values]` 뒤에 뒤쪽 인덱스를 대입해서, **학생이 빈칸을 건너뛰고 뒤엣것부터 채우면 배열에 구멍**이 생기고 JSON으로 굳으면서 `null`이 됐다.

고치는 도중 **두 번째 버그**가 회귀 테스트에서 드러났다 — `Array.every`는 **구멍을 건너뛴다.** 저장 전(메모리)에는 구멍인 채라, 건너뛴 빈칸이 검사에서 통째로 빠져 "다 채웠다"로 통과했다(`requireAnswerToAdvance`가 무력했다).

**고친 것**
- `Cloze.tsx` `isAnswered` — 빈칸 개수만큼 **인덱스로 직접** 확인(구멍·null·짧은 배열 전부 미응답)
- `Cloze.tsx` Viewer `setValue` — 조밀한 배열을 만들어 구멍을 애초에 안 만든다
- `Numeric`·`Drawing`의 `isAnswered`도 같은 유형이라 한 줄씩 방어(터지면 피해가 화면 전체다)
- `Code.gs`는 손댈 것이 없었다 — `gradeCloze`가 이미 `values[i] || ''`로 막고 있고 서버엔 `isAnswered`가 없다(규칙 4 확인 완료)

### 세션 7 — 수식 채점: 물리 키보드 "*" ≠ 버튼 "×" 오채점 버그 수정 (2026-07-31)

**증상**: 사용자가 "수식 블록에서 키보드로 입력한 수식과 버튼 입력한 수식 일부가 다른 것으로 취급돼 정답을 입력해도 인정 안 되는 경우가 있다"고 보고 — 등호·괄호·+,-,*,/ 기호들이 물리 키보드와 버튼 입력 간에 같은 것으로 취급되는지 확인해달라는 요청.

**원인**: `node_modules/mathlive/mathlive.js`의 기본 inline shortcut 테이블(`"*": "\\cdot"`, 11891행)을 직접 grep해 확인 — MathLive는 물리 키보드로 `*`를 치면 자동으로 `\cdot`을 삽입하는데, 이 앱의 "×" 버튼(`lib/mathKeyboards.ts`의 `basic` 레이어)은 `\times`를 삽입한다. 둘 다 곱셈을 뜻하지만 텍스트가 달라 `mathNormalize.ts`의 `normalizeLatex`가 이 둘을 동치로 안 봐서, 버튼으로 정답을 등록한 문항에 학생이 물리 키보드 `*`로 같은 값을 입력하면 오답 처리됐다(반대 방향도 마찬가지). `=`·`(`·`)`·`+`·`-`·`/`는 직접 mathlive.js 소스를 확인해 물리 키보드와 버튼 입력이 최종적으로 같은 LaTeX를 만듦을 확인함(`/`는 mathlive 기본 키바인딩이 `\frac{#@}{#?}`를 삽입해 버튼의 `\frac{#?}{#?}`와 결과적으로 동일 구조가 됨, `(`/`)`는 `smartFence`가 만드는 `\left`/`\right`를 `normalizeLatex`가 이미 제거하고 있었음 — 세 기호는 이미 문제 없었다).

**수정**: `src/lib/mathNormalize.ts`와 `apps-script/Code.gs`(GAS 사본, CLAUDE.md 규칙 4에 따라 둘 다 수정) 양쪽의 `normalizeLatex`에 `\cdot`(뒤에 글자가 안 이어지는 경우만 — `\cdots`·`\cdotp`는 다른 명령이라 건드리지 않음)을 `\times`로 통일하는 정규화 단계 추가. 기존 `divToFrac`(÷ 버튼 vs 분수 버튼 표기 차이 해소)과 같은 종류의 수정.

**검증**: `mathNormalize.test.ts`에 테스트 2개 추가(`\cdot`↔`\times` 동치 확인, `\cdots`/`\cdotp`는 안 건드리는지 확인) — 정규식 자체도 Node로 직접 실행해 `3\cdot4`→`3\times4`, `1,2,\cdots,n`(안 바뀜), `3\cdotp4`(안 바뀜) 확인. typecheck·test(198개, 196→198)·build 전부 통과.

**검증(실배포, live 백엔드) — 사용자 지시로 진행, 여기서 실제 버그를 발견**: 실사이트(`chan7881.github.io/class`)에서 새 수업을 만들어 URL 임베드 블록의 "파일 업로드" 모드로 실제 HTML(버튼 누르면 숫자가 올라가는 카운터)을 업로드 → 처음 설계(Drive에 저장 + `Code.gs`의 새 `doGet(?action=simHtml&fileId=...)` 라우트로 서빙)로는 업로드 자체는 성공했지만, `curl -D -`로 서빙 URL의 응답 헤더를 직접 찍어봐서 `Content-Type: text/plain`인 것을 확인(1차 버그 — `ContentService.createTextOutput(...).setMimeType(HTML)`이 실제로는 text/plain을 반환한다는, 문서만 봐선 안 드러나는 Apps Script의 실제 동작). `HtmlService.createHtmlOutput()`으로 바꿔 재배포 후 다시 curl로 확인하니 Content-Type은 고쳐졌지만, 이번엔 본문이 순수 HTML이 아니라 Apps Script 웹앱이 항상 씌우는 자체 UI 부트스트랩 페이지(Material 아이콘 스타일시트·"악용 신고" 링크·이중 iframe 샌드박스 JS)로 나오는 것을 확인(2차 문제 — 학생이 볼 콘텐츠에 안 어울리는 Google 자체 UI 껍데기). 두 시도 다 "이 앱이 doPost 전용 JSON API로 통일돼 있어 iframe이 요청하는 GET을 처리할 방법이 없다"는 이유로 새 GET 라우트가 필요했던 건데, 애초에 서버에 저장·서빙할 필요 없이 **업로드한 HTML을 수업 JSON 안에 그대로 담아 `srcdoc`으로 렌더링**하면 이 문제 자체가 사라진다는 걸 깨닫고 3번 항목처럼 재설계 — `Code.gs`는 두 번의 실험(도합 3번 재배포, 버전 8→9→10)을 전부 되돌려 세션 6 시점 원본과 기능적으로 동일하게 만들고 다시 재배포해 원상복구했다. 재설계 후에는 업로드가 순수 클라이언트 동작(`file.text()`)이 되고 렌더링도 `srcdoc`이라 mock/live 백엔드 모드 차이가 아예 없어져, 추가 실배포 검증이 불필요해졌다.
   - **자동화 환경 특이사항**: mock 모드에서 blob: URL 방식으로 실험할 때, 이 세션에서 쓰는 Chrome 확장이 `blob:` URL을 가진 iframe이 페이지에 하나라도 있으면 그 탭 전체에서 JS 실행·스크린샷이 막히는 현상을 겪었다(`"Extension manifest must request permission to access this host"`) — 완전히 새 탭을 열어야 풀렸다. 재설계 후(`srcdoc`, blob URL 안 씀)에는 이 문제 자체가 없어졌다.

**교훈**: "표준 API가 문서대로 동작할 것"이라고 가정하지 않고 curl로 실제 응답을 직접 찍어봐서 두 단계 버그(Content-Type 오류 → 원치 않는 UI 래핑)를 순서대로 발견했다 — mock 모드 검증만으로는 둘 다 절대 못 잡았을 종류의 문제(mock은 `URL.createObjectURL`이 Blob의 type을 그대로 존중해 애초에 이 문제 자체가 안 생겼음). 사용자가 "배포하고 테스트하라"고 명시적으로 요청하지 않았다면 이 버그가 실사용 시점까지 발견 안 됐을 것.

### 세션 5 — 다크모드 일관성 + 화면 여백 (2026-07-30)

**근본 원인**: Tailwind v4는 `bg-neutral-50`·`text-neutral-900` 같은 유틸리티 클래스를 실제로는 `background-color: var(--color-neutral-50)`처럼 CSS 변수 참조로 컴파일한다(프로덕션 빌드 결과물을 직접 grep해서 확인). 그런데 `src/index.css`의 다크모드 대응은 지금까지 `body`의 `color`/`background`만 수동으로 값 지정하고 있었을 뿐, 정작 이 토큰들(`--color-neutral-*`, `--color-accent-*`, 정오답 배너에 쓰는 `--color-green/red/amber-*`) 자체는 다크모드에서 한 번도 재정의된 적이 없었다 — 그래서 본문 배경만 어두워지고 카드·입력창·버튼 등 나머지 전부는 라이트 모드 색 그대로 남아, "일부만 반응하고 일부는 안 바뀌어 글자가 안 보이는" 정확히 그 증상이 났다.

**수정**:
1. `src/index.css` — 다크모드 미디어쿼리 안에 중립 회색 11단계(0~900)·강조색 옅은 톤(50/100)·정오답 배너용 green/red/amber 관련 색까지 전부 재정의. Tailwind의 `@layer`(계층) 밖에 있는 일반 CSS 규칙이라 계층 안에 있는 Tailwind 기본값보다 항상 우선한다는 CSS cascade layers 규칙을 이용해, **컴포넌트 파일을 한 줄도 안 고쳐도 앱 전체가 일관되게 반응하도록** 만들었다. `--color-white`는 의도적으로 안 건드렸다 — 버튼 위 흰 글자(`text-white`)처럼 배경이 안 바뀌는 곳에 얹는 흰색은 테마와 무관하게 항상 흰색이어야 하기 때문.
2. `bg-white`(고정 흰색, 원래는 "카드/입력창 배경"으로 20여 개 파일에서 관행적으로 써왔다) → `bg-neutral-0`(다크모드에서 실제로 뒤집히는 토큰)으로 전부 교체. `text-white`(버튼 등 색이 있는 배경 위 글자)는 반대로 그대로 뒀다 — 이 둘을 구분하지 않고 한꺼번에 처리했으면 버튼 글자가 오히려 안 보이게 됐을 것.
3. **`math/MathField.tsx`** — MathLive의 `<math-field>` 커스텀 엘리먼트는 감싸는 `<div>`(`bg-neutral-0`)의 배경을 상속하지 않고 자기 자신이 흰 배경·검은 글자를 직접 그린다(MathLive 공식 문서로 확인 — 배경·글자색은 커스텀 엘리먼트 자체에 CSS로 줘야 반영됨). 다크모드에서 카드는 어두워졌는데 수식 입력칸만 흰 박스로 남는 원인이었다 — `field.className`에 `bg-neutral-0 text-neutral-900`을 직접 추가해 해결.
4. **`components/QrCode.tsx`** — QR코드 확대 화면은 스캔 안정성 때문에 배경을 의도적으로 항상 흰색으로 남겨뒀는데(세션 4에서 이미 그렇게 결정함), 그 안의 글자들(`text-neutral-900` 등)은 그대로 토큰을 써서 다크모드에서 밝은 색으로 뒤집혀 **흰 배경 위에 흰 글자가 되는 사고**가 실제로 있었다(자동 스캔으로 발견, 대비율 1.04). 배경이 고정이면 안의 글자색도 같이 고정해야 한다는 걸 놓친 경우 — 이 카드 안에서만 회색 스케일을 인라인 스타일로 라이트 모드 값에 고정해서 해결.
5. **화면 좌우 여백** — `player/Player.tsx`의 슬라이드 본문(`SlideView`)이 다른 화면들(`PageShell` 기준 `max-w-3xl` 중앙 정렬)과 다르게 `px-4`만 있고 폭 제한이 없어, 데스크톱 브라우저의 넓은 창에서 텍스트·문항이 화면 끝까지 늘어나 답답해 보였다. 다른 화면과 같은 `max-w-3xl` 중앙 정렬 컨테이너로 감쌌다 — 모바일 폭에서는 화면이 항상 그보다 좁아 레이아웃 변화가 없다(확인됨).

**검증**: 실제 발행된 수업 `VJCD6N`(live 백엔드)을 로컬 dev 서버로 직접 열어 학생 입장→슬라이드 1~4(화학식·수식 문항 포함)까지 진행하며, 브라우저에 WCAG 명도 대비 계산 스크립트를 주입해 페이지 전체의 글자색 대비 자동 스캔(대비 2.5 미만이면 사실상 안 보이는 수준으로 간주)을 실행했다. 다크모드는 이 자동화 환경에 OS 수준 전환 도구가 없어 `document.documentElement.style`에 다크모드 값과 동일한 CSS 변수를 직접 주입해 시뮬레이션했다(실제 `prefers-color-scheme` 미디어쿼리 트리거 메커니즘 자체는 표준 CSS라 별도 검증 불필요, 값 자체가 올바르게 전파되는지가 검증 대상). 홈 화면·QR 확대 화면(수정 전/후 모두 확인)·학생 슬라이드 4장·관리자 로그인 화면·에디터 "편집 키 필요" 화면까지 스캔해 위 2개 실제 버그(수식 입력칸, QR 확대 화면)를 찾아 그 자리에서 수정, 이후 재스캔에서 전부 통과했다. 화면 여백은 콘텐츠 폭이 실제로 1280px 뷰포트에서 768px로 정확히 제한되는 것을 직접 측정해 확인.
   - **참고**: 검증 도중 발견한 재미있는 허위 양성 사례 — "다음" 버튼(잠김 상태, `transition-colors` 적용)이 대비 1.48로 잡혔는데, 원인은 실제 색상 버그가 아니라 이 자동화 브라우저 탭이 백그라운드로 처리되며 CSS 트랜지션이 멈춘 채로 스냅샷된 것이었다(`transition-colors` 클래스를 껐다 켜서 강제로 리플로우하니 즉시 올바른 값으로 재계산됨). 실제 사용자는 탭이 항상 포그라운드이므로 이 현상을 겪지 않는다 — 자동화 환경 특유의 아티팩트로 판단하고 실제 버그로 취급하지 않았다.

### 세션 3 후속 — 수식 문항 입력 버그: 분수 등 구조형 버튼이 안 채워지던 근본 원인 (2026-07-29)

영문자 입력 수정 이후 사용자가 "분수 식이라던지 안 먹히는 문자들이 생김"을 신고. 원인은 `mathKeyboards.ts`의 분수·근호·첨자 버튼들이 `\frac{}{}`처럼 **빈 중괄호**로 구조를 삽입하고 있었던 것 — MathLive의 `insert()`는 삽입 직후 "첫 번째 빈 플레이스홀더"를 자동 선택하는데(`selectionMode: 'placeholder'`가 기본값), 빈 `{}`는 진짜 플레이스홀더로 인식되지 않아 커서가 구조 밖에 남고, 그다음 버튼 입력이 구조 안으로 안 들어갔다. **`node_modules/mathlive/mathlive.js`의 실제 소스**(`"frac": "\\frac{#?}{#?}"`, MathLive 자체 기본 키보드 정의)를 직접 읽어 `#?`가 진짜 채움칸 토큰(내부적으로 `\placeholder{}` atom이 됨)이라는 걸 코드로 확인 — 문서(`InsertOptions.selectionMode` 설명)만으론 확신이 안 서서 소스까지 대조했다. `mathKeyboards.ts`의 `\frac{}{}`/`\sqrt{}`/`\sqrt[]{}`/`\left|\right|`/`\log_{}`/`e^{}`/위·아래첨자 버튼 전부를 `#?`로 교체. **브라우저로 실제 검증**: "a/b" 클릭 → `\frac{\placeholder{}}{\placeholder{}}` 생성 확인 → "1","2" 버튼 클릭 → `\frac{12}{\placeholder{}}`로 정확히 분자에 들어가는 것까지 확인(전엔 이 검증 자체를 안 해봐서 놓쳤던 버그 — 7단계 브라우저 검증이 "7+8" 같은 단순 버튼만 테스트했고 분수·근호류는 한 번도 실클릭 검증을 안 했었다).

### 실배포 검증 중 발견한 버그 — 제출 직후 뒤늦은 자동저장이 "미제출"로 되돌리는 경쟁 조건
- **증상**: 학생이 문항에 답하고 곧바로 "제출하기"를 눌러 "제출 완료!" 화면까지 봤는데도, 교사 결과 대시보드에는 그 학생이 "진행중"(미제출)으로 남아 있었다.
- **원인**: `Player.tsx`의 자동저장은 답이 바뀔 때마다 1.5초 디바운스로 `saveProgress`를 부르는데, 이 페이로드에는 애초에 `submittedAt` 필드가 없다(`Omit<ResponseRecord,'submittedAt'>`). 학생이 답을 고르자마자 곧바로 "제출하기"를 누르면, 그 직전에 예약된 자동저장이 **제출(`submitResponse`)보다 늦게 서버에 도착**할 수 있고, 이게 그대로 저장되면 방금 기록된 `submittedAt`을 지워버린다. mock 모드는 모든 호출이 사실상 동기(즉시)라 이 틈이 벌어질 일이 없었지만, 실제 Apps Script는 호출마다 수 초가 걸려 이 경쟁이 실제로 재현됐다.
- **수정**: 서버 쪽(`mock.ts`/`Code.gs` 둘 다) `saveProgress`에 "이미 `submittedAt`이 있는 응답은 그대로 두고 무시한다"는 방어를 추가(POE `enforceLocks`와 같은 철학 — 한 번 확정된 필드는 뒤늦은 요청이 되돌리지 못하게 서버가 지킨다). 클라이언트(`Player.tsx`)에도 "제출하기"를 누르는 순간 예약돼 있던 자동저장 타이머를 명시적으로 취소하는 방어를 추가해 애초에 경쟁이 덜 발생하게 함. `mock.test.ts`에 회귀 테스트 추가, 실제 배포에도 동일하게 반영하고 재배포 후 브라우저에서 직접 재현·수정 확인함.
- **교훈**: mock 백엔드는 즉시 실행되기 때문에 "쓰기 순서가 뒤바뀌는" 종류의 버그를 원천적으로 숨긴다. Apps Script처럼 정말 네트워크 지연이 있는 실제 배포로 전체 플로우를 검증하기 전까지는 이런 경쟁 조건이 있어도 알 수 없다 — `docs/PLAN.md`가 "실제 배포 후에도 7~14번 반복 검증"을 요구한 이유가 실제로 여기서 입증됐다.

- **claude-in-chrome의 `computer` 툴(click/screenshot)이 이 세션 내내 불안정**했다 — `Page.captureScreenshot`이 매번 타임아웃되고, 프로그래매틱 `.focus()`/`.click()` 후에도 `document.hasFocus()`가 계속 `false`(이 자동화 탭이 OS 차원에서 "포그라운드"로 취급되지 않는 것으로 보임 — TipTap의 `editor.isFocused`가 이 값에 의존해서 버블 툴바 표시 여부를 자동화로는 확인 못 함, 명령 자체는 `editor.chain()...run()`으로 직접 검증함). **우회책**: `javascript_tool`로 실제 DOM에 `input`/`click` 이벤트를 직접 디스패치하고 `document.body.innerText`·`localStorage` 상태로 결과를 확인하는 방식이 이 세션 내내 안정적으로 동작했다. 다음 세션에서도 `computer` 툴이 같은 증상(스크린샷 타임아웃, 포커스 안 잡힘)을 보이면 재시도하지 말고 바로 `javascript_tool` 우회로 전환할 것.
- **SPA 같은 라우트로의 네비게이션은 컴포넌트를 리마운트하지 않는다** — 이번 세션에서 이걸 모르고 "복구 링크(`?key=`)가 안 먹힌다"고 착각할 뻔했다. `navigate` 툴이나 `location.href=`로 **같은 경로, 다른 쿼리** URL을 열어도 React Router가 같은 라우트 엘리먼트를 재사용해 `useState` 초기값이 다시 안 읽힌다. 새 마운트를 확인해야 하는 테스트(예: localStorage 초기 읽기, `?key=` 처리)는 반드시 `location.reload()`로 강제 새로고침해서 검증할 것 — `navigate`만으로는 오탐이 난다.
- **`javascript_tool`이 "CDP Runtime.evaluate timed out after 45000ms"를 던져도 페이지 안의 스크립트는 계속 실행 중일 수 있다.** 4단계에서 이걸 몰라서 타임아웃 = 실패로 오판하고 같은 삽입 동작을 수동으로 반복했다가 문항이 중복 삽입된 적이 있다(정리함). **타임아웃을 받으면 곧바로 같은 동작을 재시도하지 말고, 먼저 `localStorage`나 화면 상태를 읽어 실제로 실패했는지부터 확인할 것.**
- **네이티브 `confirm()`/`alert()`를 띄우는 버튼을 자동화로 클릭하면 CDP 연결 전체가 멈춘다** — 2026-07-29에 결과 페이지의 "수업 데이터 완전 삭제"(`window.confirm` 확인 후 삭제) 버튼을 클릭했더니 `Input.dispatchMouseEvent`/`Runtime.evaluate` 등 이후의 모든 CDP 명령이 타임아웃났다(대화상자가 렌더러를 블로킹). **삭제·발행 취소처럼 `confirm()`을 거치는 것으로 보이는 버튼은 자동화로 클릭하기 전에 먼저 소스에서 `window.confirm` 사용 여부를 확인하고, 있다면 클릭을 사용자에게 넘길 것.** 이미 멈춘 탭은 되살릴 수 없으므로(재시도해도 계속 타임아웃), `tabs_context_mcp`로 새 탭을 열어 다른 작업을 이어가고 사용자에게 원래 탭에서 대화상자를 직접 눌러달라고 안내하는 것이 유일한 대응이다.
- **claude-in-chrome이 여는 탭은 `document.hidden:true`(OS 포그라운드가 아님)로 유지된다** — 9단계에서 `ClassAggregate`의 `IntersectionObserver` 기반 폴링이 이 때문에 자동화로는 안 켜짐을 확인했다(기존 `document.hasFocus()` 항상 false 이슈와 같은 근본 원인으로 추정). 앞으로 `IntersectionObserver`·`requestIdleCallback`·Page Visibility API에 의존하는 기능을 자동화로 검증할 때는, 먼저 `document.hidden`을 확인하고 `false`가 안 되면 실제 폴링/옵저버 발동 대신 (1) 백엔드 API를 직접 호출해 데이터 정합성만 확인하거나 (2) React 파이버의 훅 `dispatch`를 직접 호출해 상태만 강제로 켜서 나머지 로직(폴링·렌더링)이 맞는지 확인하는 우회로 검증할 것(자세한 방법은 `docs/DECISIONS.md` 2026-07-28 항목 참고).
- ~~세션 3(2026-07-29) 초반엔 claude-in-chrome 확장 자체가 연결되지 않았다~~ **같은 세션 후반에 사용자가 Chrome을 직접 띄워 확장이 연결됐고, 서브에이전트 3개를 병렬로 띄워 14건 전체를 브라우저로 실클릭 검증까지 마쳤다**(위 "세션 3" 절 참고). 확장이 다시 연결 안 되는 경우가 재발하면 `tabs_context_mcp`가 "Browser extension is not connected"를 반환하는지부터 확인할 것 — 그때는 이전처럼 코드 리뷰 수준으로만 진행하고 사용자에게 알릴 것.
- **서브에이전트로 브라우저를 병렬 조작할 때, 같은 Chrome 세션/탭 그룹을 다른 세션(사용자 본인의 수동 조작 포함)과 동시에 공유하면 탭이 예기치 않게 다른 URL로 튕기거나 닫힐 수 있다** — 세션 3의 검증 에이전트 2개가 이 현상을 겪었다(자기가 만든 탭이 낯선 `/play/<code>` 화면으로 바뀌거나 닫힘). 코드 문제는 아니었고 새 탭으로 재시작하는 것으로 우회됐다. 여러 에이전트를 동시에 브라우저에 붙일 때는 이 가능성을 감안하고, 결과가 이상하면 먼저 "다른 세션이 같은 탭을 건드렸을 가능성"부터 의심할 것.
- **이 환경의 `resize_window` 툴이 실제로 뷰포트 크기를 바꾸지 못하는 경우가 있었다**(세션 3, 모바일 폭 390px 요청했는데 `window.innerWidth`가 그대로 ~1045px). 모바일 반응형 검증이 꼭 필요하면 이 툴이 정말 반영됐는지 `window.innerWidth`로 먼저 확인하고, 안 먹히면 실제 모바일 기기나 다른 방법을 쓸 것.
