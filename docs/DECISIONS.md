## 2026-07-28 백엔드 아키텍처 — 중앙 배포 Apps Script + GitHub Pages

**결정**: 프론트엔드는 React+Vite+TS로 GitHub Pages에 정적 배포. 백엔드는 운영자 계정에 Google Apps Script 웹앱을 **한 번만 배포**해 모든 교사가 공유. 데이터는 운영자 Drive(수업 JSON·미디어)와 Sheets(응답)에 저장.

**이유**: 별도 서버 구축이 요구사항에서 제외되어 있었고, 교사가 설정 없이 바로 쓸 수 있어야 했다. Apps Script는 무료이고 스프레드시트 자체가 "엑셀로 답안 수합" 요구를 자연스럽게 만족시킨다.

**버린 대안**:
- *교사별 개인 배포* — 개인정보가 교사 본인 계정에만 남아 가장 안전하지만, 교사마다 5분짜리 설정이 필요해 "교사가 설정 없이 바로 쓴다"는 목표와 충돌. 사용자가 중앙 배포를 선택.
- *Apps Script 단독 호스팅(HtmlService)* — 배포가 한 번으로 끝나지만 iframe 샌드박스 제약, 느린 로딩, 개발 편의성 저하로 기각.
- *Firebase(Firestore)* — 실시간 동기화엔 유리하나 별도 프로젝트 생성·요금제 확인이 필요해 "서버 구축 없이"라는 제약과 어긋나 기각.

## 2026-07-28 수식·화학식 입력 — MathLive, 버튼 전용, 자동변환 없음

**결정**: 수식 입력은 MathLive(`<math-field>`) + 커스텀 가상 키보드 5종(basic/fraction/greek/unit/chem)을 쓴다. 화학식은 별도 입력칸에 위/아래첨자 **토글 버튼**을 눌러 입력하며, `H2O → H₂O` 같은 자동 변환은 하지 않는다.

**이유**: 사용자가 "학생은 LaTeX 문법을 모른다고 가정해야 한다"고 명시적으로 지시했고, 화학식 첨자도 "자동변환보단 별도 버튼"으로 명시했다. MathLive는 시각 편집 + 커스터마이즈 가능한 버튼 키보드를 지원하면서 출력이 LaTeX 문자열이라 채점(`lib/grade.ts`)과의 연동이 쉽다.

**버린 대안**:
- *일반 텍스트 입력 + LaTeX 직접 타이핑* — 가장 구현이 쉽지만 사용자 제약과 정면으로 충돌해 기각.
- *H2O 자동 첨자 변환* — 입력 편의는 좋지만 사용자가 명시적으로 "자동변환보단 버튼"을 요청해 기각.
- *수식은 symbolic 비교만 지원* — `@cortex-js/compute-engine` 상시 로드는 번들이 무거워, 기본은 정규화 문자열 비교로 하고 symbolic은 옵션 문항에서만 동적 import 하기로 함.

## 2026-07-28 Node.js 설치 — winget 실패 → 사용자 폴더에 zip 압축 해제

**결정**: `winget install OpenJS.NodeJS.LTS`가 이 환경에서 동작하지 않아, Node.js 22 LTS의 Windows x64 **zip 배포판**을 직접 받아 `%LOCALAPPDATA%\Programs\nodejs`에 압축 해제하고, 사용자 PATH 환경변수(HKCU, 관리자 권한 불필요)에 등록했다.

**이유**: 확인해보니 (1) 이 셸에 `winget.exe`가 PATH에 없었고(App Installer 패키지는 등록돼 있으나 alias 미해결), (2) 현재 세션이 관리자 권한이 아니어서 공식 MSI 설치도 `1603`(치명적 오류, HKLM/Program Files 쓰기 거부로 추정)으로 실패했다. Node.js 공식 zip 배포판은 설치 프로그램 없이 그대로 실행 가능해 관리자 권한 문제를 완전히 우회한다.

**버린 대안**:
- *winget 재시도* — PATH에 실행 파일 자체가 없어 재시도로 해결될 문제가 아니었음.
- *MSI를 관리자 권한으로 재시도* — 이 자동화 환경은 UAC 대화형 승격을 처리할 수 없어(현재 세션 비관리자, 승격 시 사용자 확인 필요) 무인 설치가 불가능. 사용자에게 별도로 요청할 수도 있었지만, zip 방식이 사용자 개입 없이 즉시 해결 가능해 우선 적용.
- *nvm-windows 등 버전 관리자 설치* — 장기적으로는 더 편하지만, 그 설치 자체도 관리자 권한이 필요할 수 있어 이번엔 보류. 필요해지면 나중에 재검토.

## 2026-07-28 react-router-dom 취약점 경고 — 다운그레이드 없이 최신 유지

**결정**: 1단계 스캐폴딩 중 `npm audit`이 `react-router-dom@7.18.1`(설치된 최신 버전)을 high severity로 표시했다(`GHSA-qwww-vcr4-c8h2`, "RSC Mode CSRF Bypass Allows Action Execution Before 400 Response", 영향 범위 7.12.0~8.2.0). `npm audit fix --force`는 7.11.0으로 **다운그레이드**를 제안하지만 적용하지 않고 7.18.1을 그대로 쓰기로 했다.

**이유**: 이 취약점은 React Router의 **RSC(React Server Components) 모드**와 서버 loader/action 실행 경로에 한정된다. 이 프로젝트는 GitHub Pages에 배포되는 순수 정적 SPA이고 HashRouter로 클라이언트 사이드 라우팅만 하며, React Router의 데이터 API(loader/action)나 RSC는 애초에 쓰지 않는다. 따라서 이 벡터는 이 앱에 적용되지 않는다. 7 버전을 통째로 낮추면 이후 단계에서 다른 회귀를 만들 위험이 더 크다고 판단했다.

**버린 대안**:
- *`npm audit fix --force`로 7.11.0 다운그레이드* — 실제로 안전해지는 것 없이(우리는 취약 코드경로를 안 씀) 7개 마이너 버전의 개선사항을 잃는다.
- *react-router-dom을 아예 안 쓰고 직접 라우팅 구현* — 4개 뿐인 페이지라 가능은 하지만, 검증된 라이브러리를 버리고 직접 구현한 라우터의 버그 위험을 새로 떠안는 것이 더 나쁜 선택.

**주의**: 앞으로 이 프로젝트에 React Router의 loader/action이나 RSC 모드를 도입하는 결정을 내릴 일이 생기면, 이 취약점이 실제로 적용되는지 그때 다시 확인할 것.

## 2026-07-28 3단계 에디터 — 슬래시 메뉴는 "+" 버튼으로, 실시간 "/" 감지는 생략

**결정**: 블록 삽입 UI는 각 블록 hover 시 나타나는 "+" 버튼과 캔버스 하단의 "+ 블록 추가" 버튼으로 연다. Notion처럼 빈 문단에 "/"를 타이핑하면 바로 메뉴가 뜨는 실시간 키 입력 감지는 구현하지 않았다.

**이유**: "/" 감지를 제대로 하려면 특정 블록(TextBlock)의 TipTap 에디터 안에서 일어난 일을 상위 Canvas(블록 배열 자체를 바꿔야 함)로 끌어올려야 하는데, 이게 BlockEditorProps 계약(`onChange: (next: B) => void`, 같은 타입끼리만 교체 가능)을 깨거나 별도 콜백을 추가해야 해서 복잡도가 크게 늘어난다. 반면 "+" 버튼은 Notion 자신도 모바일 앱에서 기본으로 쓰는 방식이고, 이 프로젝트가 "모바일 환경에서 잘 작동"을 요구사항으로 명시했다는 점에서 오히려 터치 입력에 더 적합하다(모바일 키보드에서 "/"를 치는 것 자체가 번거로움).

**버린 대안**:
- *`@tiptap/suggestion`로 진짜 "/" 커맨드 구현* — 패키지 자체는 있지만, "다른 블록 타입으로 교체"라는 우리 아키텍처(블록마다 독립된 TipTap 인스턴스)에는 그대로 맞지 않아 상당한 추가 배선이 필요. 가치 대비 복잡도가 안 맞다고 판단해 보류. 나중에 사용자 피드백으로 꼭 필요해지면 재검토.

## 2026-07-28 3단계 에디터 — 되돌리기(undo/redo)는 구조적 변경만 기록

**결정**: 슬라이드·블록 추가/삭제/재정렬/보조슬라이드 지정 같은 "구조적 변경"만 `editorStore`의 되돌리기 스택에 쌓는다. 리치텍스트 타이핑, 문항 옵션 수정 같은 "내용 변경"(`updateBlock`)은 스택에 안 남긴다.

**이유**: 모든 키 입력마다 수업 전체 스냅샷을 되돌리기 스택에 쌓으면 (a) 스택이 몇 글자만 쳐도 금방 차고 (b) Ctrl+Z 한 번이 "글자 하나 지움" 수준이 되어 실제로 쓸모없는 되돌리기가 된다. 리치텍스트 타이핑 자체의 되돌리기는 TipTap/ProseMirror가 필드 단위로 이미 제공한다(각 텍스트 상자 안에서 Ctrl+Z 하면 그 상자의 타이핑 히스토리가 따로 동작).

**버린 대안**:
- *모든 변경을 스냅샷* — 위 이유로 기각.
- *디바운스해서 일정 시간마다 스냅샷* — 그래도 "무엇을 되돌리는지"가 사용자에게 예측 불가능해서 기각. 구조적 변경 단위가 더 명확하다.

## 2026-07-28 3단계 에디터 — 미리보기는 Viewer 나열, 우측 속성 패널은 생략

**결정**: `docs/PLAN.md`는 "미리보기"가 실제 플레이어 컴포넌트를 읽기 전용으로 재사용하고, 에디터에 "우 선택 블록 속성 패널"이 따로 있다고 적었다. 3단계에서는 둘 다 단순화했다: 미리보기는 현재 슬라이드의 Viewer 컴포넌트들을 그대로 나열만 하고(진행 잠금·다음 버튼 없음), 블록별 속성(이미지 폭, 영상 구간 등)은 별도 패널이 아니라 각 블록의 Editor 컴포넌트 안에 인라인으로 넣었다.

## 2026-07-28 TipTap 확장 — `@tiptap/extension-color`/`font-family` 대신 `TextStyleKit` 사용

**결정**: 별도 `@tiptap/extension-color`, `@tiptap/extension-font-family` 패키지와 직접 만든 `FontSizeExtension.ts`를 쓰려다, `@tiptap/extension-text-style`가 이 버전(v3)에서 이미 `TextStyleKit`(Color+FontFamily+FontSize+BackgroundColor+LineHeight+TextStyle 번들)을 공식 제공한다는 걸 확인하고 그걸로 교체했다.

**이유**: 직접 만든 FontSize 확장이 공식 것과 커맨드 이름(`setFontSize`/`unsetFontSize`)까지 완전히 같아서 중복이었고, 패키지도 하나로 줄어든다. `lineHeight: false`로 안 쓰는 기능만 꺼서 씀.

**버린 대안**: 커스텀 `FontSizeExtension.ts` 유지 — 코드가 늘어나기만 하고 이점이 없어 삭제.

## 2026-07-28 4단계 연결형(match) 문항 — 드래그 연결선 대신 탭-투-페어

**결정**: `docs/PLAN.md`에는 연결형 문항의 정확한 인터랙션이 정해져 있지 않았다. 왼쪽↔오른쪽을 선으로 잇는 드래그 방식 대신, 왼쪽 항목을 탭하고 이어서 오른쪽 항목을 탭하면 짝이 완성되는 **탭-투-페어** 방식으로 구현했다.

**이유**: 이 프로젝트는 모바일 우선이 명시적 요구사항이다. 두 열 사이를 손가락으로 정확히 드래그해 선을 긋는 인터랙션은 작은 화면·터치 입력에서 오조작이 잦고 구현도 복잡한(SVG 선 그리기, 드래그 중 스크롤 처리 등) 반면, 탭-투-페어는 버튼 클릭 두 번으로 끝나 터치 정확도 요구가 낮고 dnd-kit 같은 별도 드래그 라이브러리도 필요 없다.

**버린 대안**: SVG로 선을 그리는 진짜 드래그 연결 — 시각적으로는 더 "연결형답게" 보이지만, 모바일 터치 정확도·구현 복잡도 대비 이득이 크지 않다고 판단. 데스크톱 사용성을 더 중시하게 되면 재검토.

## 2026-07-28 4단계 순서배열(order) 문항 — 학생 화면 셔플은 새로고침마다 다시 섞일 수 있음 (알려진 한계)

**결정**: 학생에게 보여줄 때 `question.items`를 `useMemo(() => shuffle(items), [question.id])`로 한 번만 섞고 그 이후 리렌더에는 유지한다. 하지만 학생이 페이지를 새로고침하면 컴포넌트가 새로 마운트되며 다시 섞인다 — 시드를 고정하지 않았다.

**이유**: 완벽히 고정하려면 `studentKey + questionId`를 시드로 하는 결정적 셔플이 필요한데, 지금 단계에서는 우선순위가 낮다고 판단해 미룬다. 실제로 문제가 되는 상황은 "학생이 순서를 절반쯤 맞추다가 새로고침"인데, 5단계(플레이어 자동저장)에서 `value`(학생이 만든 현재 순서)를 저장해두면 그 값이 있을 때는 셔플 결과 대신 저장된 순서를 그대로 쓰도록 이미 코드에 들어있다(`order.length === items.length`인 값이 있으면 그걸 우선) — 그래서 실제 영향은 "한 번도 안 건드린 상태로 새로고침하면 보이는 순서가 바뀐다" 정도로 작다.

## 2026-07-28 8단계 — 데이터표 계산 열 파서: `Object.hasOwn`으로 프로토타입 체인 우회

**결정**: `lib/formula.ts`의 열 참조 평가에서 `ctx.row[name]`을 바로 읽지 않고 `Object.hasOwn(ctx.row, name)`으로 소유 속성인지 먼저 확인한다.

**이유**: 테스트를 작성하다가 `evaluateFormulaString('__proto__', { row: {}, columns: {} })`가 오류를 던지지 않고 `Object.prototype`을 반환하는 걸 발견했다 — 일반 객체에서 `obj['__proto__']`는 `undefined`가 아니라 실제 프로토타입 객체를 돌려주는 접근자이기 때문이다. 코드 실행으로 이어지진 않지만(애초에 `eval`을 안 쓰므로), 정의 안 된 열을 참조했을 때 오류 대신 조용히 이상한 비-숫자 값이 계산에 섞여 들어갈 수 있는 실제 버그였다. `Object.hasOwn`으로 소유 속성만 걸러 정확히 "정의되지 않은 열"로 처리되게 고쳤다.

**버린 대안**: `__proto__`/`constructor` 같은 이름을 블록리스트로 걸러내는 방식 — 이름 목록을 유지보수해야 하고 다른 우회 경로(예: `toString`, `valueOf`)를 놓칠 위험이 있어, `hasOwn` 하나로 일반화해 해결하는 쪽을 택했다.
